11. Incidents and drills

Real problems met while building, with their evidence and root causes (full reports in docs/incident-reports/), and the planned drills (docs/drills/). Each one changed the code so it cannot happen again.

11.1 INC-001: VPN handshakes dropped

Symptom: after the WireGuard gateway was deployed, the admin client could not keep a tunnel up. Evidence: gw01 received and answered every handshake, but the answers never reached the client; in a controlled test on the same port and path, plain UDP made the round trip while WireGuard traffic did not. Root cause (high confidence): something on the network path recognises WireGuard by its fixed handshake sizes and header bytes and drops it. Changing the port would not help. Fix: WireGuard carried inside TLS on TCP 443 by wstunnel (D-040), which looks like HTTPS. Lesson: prove a network hypothesis with a controlled comparison before redesigning.

11.2 INC-002: site.yml froze

Symptom: during lab.sh up the Ansible run produced no output for over 30 minutes; lab.sh resume then finished normally. Evidence: package histories showed that no host was running a package task while it was frozen. Root cause: not proven; a stalled Instance Connect SSH session is the strong candidate. Fix: logging to ~/ansible.log, SSH keepalives, a 30-minute task timeout, and long jobs run detached on control01 and polled (run_on_control01). Lesson: say honestly when a root cause is not proven, and make the system robust to the likely causes.

11.3 INC-003: firewalld "not running" on a fresh host

A task failed one second after firewalld was started. firewalld is a D-Bus service: systemd marks it "started" as soon as it owns its D-Bus name, before it has loaded its configuration. Fix: wait until firewall-cmd --state answers. Lesson: "the service started" is not "the service is ready".

11.4 INC-004: fresh build hung on workstation dnf

The first rebuild after workstations lost direct internet (D-057) hung in dnf on ws-dev01: they now needed Squid for packages, but Squid did not exist yet and dnf had no proxy setting. D-057 had been tested on a running lab, never from scratch. Fix: site.yml patches util01 and builds Squid first, then points workstations' dnf at it by IP. Lesson: every change to build order must be tested from nothing.

11.5 INC-005: leaked IAM key used for Amazon Bedrock

AWS emailed that the account had accepted an agreement for a model on Amazon Bedrock, which nobody had done. CloudTrail showed a second IAM user's long-term access key with administrator rights, leaked outside this project, being used from an unknown machine. It was blocked within minutes. Impact: $0, because every model call was throttled. Actions: the account was reduced to the root user (MFA) and one IAM user (MFA, one rotated key); every other user, role, admin group and the GitHub OIDC provider were deleted. Lesson: long-lived admin keys are the classic cloud breach; use MFA, least privilege and short-lived credentials.

11.6 INC-006: control01's IP taken by the Instance Connect Endpoint

A fresh build failed with InvalidIPAddress.InUse: 10.0.1.10. The Instance Connect Endpoint, created earlier in the same apply, had been given control01's fixed address by AWS. AWS-managed interfaces take any free address, and nothing reserved the hosts' fixed IPs; earlier builds had passed by luck (roughly 1% per build). Fix: explicit subnet CIDR reservations 10.0.x.8/29 (D-062), a validation that every host IP is inside its block, and tests. Lesson: a design that works "by luck" fails eventually.

11.7 INC-007: SSH offered password logins on every host

Symptom: during the CIS work, sshd -T showed kbdinteractiveauthentication yes everywhere, although our drop-in said no. Root cause: sshd keeps the first value it reads; IPA's 04-ipa.conf (with ChallengeResponseAuthentication yes, an alias) was read before our 10-ahmed-hardening.conf. The old test tried only the password method, so it passed. Impact: IPA's admin (password in the vault, in the admins group allowed everywhere) could have logged in with its password; no evidence that it happened. Fix: the drop-in renamed 01-ahmed-hardening.conf; every drop-in made to agree; a test that servers offer publickey and nothing else. Lesson: test what the system actually does (the methods offered), not one path of it.
