2.3 Terraform

Terraform describes infrastructure as code in HCL files. terraform plan compares the code with what exists and shows what it would add, change or destroy; terraform apply does it. It records what it created in a state file, the map between code and real resources. Concepts the lab uses:

  • Remote state with locking: state is stored in the S3 bucket ahmed-statefile, versioned and TLS-only; use_lockfile = true creates a lock object in S3 so two runs never write at once (D-016, D-044).
  • Layers: three separate configurations with separate states: terraform/bootstrap (the state bucket itself), terraform/persistent (things that survive teardown) and terraform/ (the lab, destroyed every session) (D-042).
  • Modules: reusable building blocks with inputs and outputs: network, security-groups, ec2-instance (D-014).
  • for_each: one block creates many resources from a map. Every host comes from one entry in the hosts map.
  • Validations: rules on input variables, for example "two hosts may not share an IP" or "a host's IP must be in its subnet's reserved block".
  • import and moved blocks: adopt an existing resource into code without recreating it; rename a resource without destroying it.
  • Ephemeral resources and write-only arguments (Terraform 1.11+): generate a value and send it to AWS without it ever being stored in state, which is how the Vault password is created.
  • lifecycle: prevent_destroy refuses to delete precious resources; ignore_changes stops Terraform from replacing servers when a newer image appears; create_before_destroy builds a replacement before removing the old one.
  • terraform test with mocked providers: tests that run in seconds without AWS credentials (D-045).

2.4 Ansible

Ansible connects to hosts over SSH and runs modules (small programs such as "install this package" or "write this file") as described in YAML playbooks. It is agentless and idempotent: a module changes something only if it is not already in the wanted state, so a second run reports changed=0. The lab's terms:

  • Control node: control01 is the only place Ansible runs, inside a Python virtual environment with pinned versions (D-028, D-030).
  • Dynamic inventory: the amazon.aws.aws_ec2 plugin asks AWS which instances exist and groups them by their Role and Team tags (role_util, team_dev, ...) (D-029). Nothing can drift because AWS is the source of truth.
  • Roles: folders of tasks, templates, handlers and defaults for one job (base, nfs_server, ...).
  • group_vars: data per group, the files you edit day to day.
  • Handlers: tasks that run only when something changed, for example "restart sshd after its config changed".
  • Templates (Jinja2): config files with variables, rendered per host.
  • Collections: packaged modules and roles: ansible.posix, amazon.aws, freeipa.ansible_freeipa, pinned in requirements.yml.
  • Ansible Vault: encrypts whole files of secrets. The password comes from SSM through scripts/vault-password.py.
  • become: run as root through sudo. pipelining streams modules over SSH without temporary files.

2.5 FreeIPA (Red Hat Identity Management)

FreeIPA is Red Hat's central identity system, the Linux equivalent of Microsoft Active Directory (D-006). One server (idm01) bundles several well-known components:

ComponentJob
389 Directory Server (LDAP)The database of users, groups, hosts, rules and SSH keys.
MIT Kerberos KDCSingle sign-on tickets; every enrolled host gets a keytab, its own Kerberos identity.
BIND DNS (integrated)Serves ahmed.internal: host records created automatically at enrollment, service records, SSHFP records (SSH host key fingerprints), reverse (PTR) records.
Dogtag CAA certificate authority that issues TLS certificates to hosts and services. The lab uses it for rsyslog's TLS.
certmongerOn clients: requests certificates from the CA and renews them before they expire.
HBAC rulesHost-Based Access Control: which users may log into which hosts. The lab has no default "allow_all" rule.
sudo rulesCentral sudo policy: who may run what as whom on which hosts.
Automount mapsCentral autofs maps: /users/<name> and /teams/<team> come from util01 over NFS.
Web UI and APIManagement over HTTPS (also from the admin VPN range).

On every other host, SSSD (System Security Services Daemon) is the client side: it answers "who is sara?" (UID, groups, home), fetches her SSH public key for sshd, checks HBAC rules during login, delivers sudo rules, serves automount maps, and caches all of it so known users keep working when idm01 is briefly down. A host joins IPA by enrollment (ipa-client-install), using a one-time password that the playbook creates for it.

2.8 Backups and the AWS CLI

Backups use two standard tools: tar (archives files with their permissions, ACLs, extended attributes and SELinux labels, and stores owners by name) and awscli2 (streams the archive straight into S3 with no temporary file). The bucket is versioned, so every backup keeps the previous ones for 30 days. No third-party backup software or repository is needed (D-056).

2.9 Where each tool came from

Everything comes from Red Hat's own repositories except: the Ansible collections (Ansible Galaxy, pinned versions), wireguard-tools (one package from EPEL through a repository definition limited to that package, D-033), and the wstunnel binary (GitHub release, pinned version, SHA-256 verified). Keeping third-party sources to these three is deliberate.
