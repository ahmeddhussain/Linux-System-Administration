9. Running the company day to day

The operations manual. The golden rule: change the data in Git, push, apply from control01, verify with the tests. Never change a server or IPA by hand except to rescue it, and then write the fix into code.

9.1 Starting and ending a working session

cd ~/ahmed-infra
eval "$(ssh-agent)"              # the bootstrap key is loaded into it by lab.sh
scripts/lab.sh up                # about an hour; expect 160 passed, 0 failed
scripts/vpn-client.sh refresh    # gw01 has a new public IP after every rebuild (needs sudo)
scripts/vpn-client.sh connect
ssh control01-vpn                # your admin entry; break-glass: ssh control01

At the end of a session:

git status                       # everything committed and pushed?
terraform -chdir=terraform plan -destroy     # review: only the lab layer (169 resources)
scripts/lab.sh down              # backs up util01 to S3, then destroys the lab
Never interrupt an apply and then destroy
If up is stopped while Terraform is still creating resources, AWS may finish creating something Terraform never recorded in its state (an orphan). The destroy then fails with DependencyViolation. Delete the orphan by its Name tag and destroy again. Better: let the apply finish, then destroy.

9.2 The change workflow (for every ticket)

  1. Write the ticket: what, why, who asked. Record a decision in Decisions.md if it changes policy.
  2. Edit the data file on the laptop; commit; push.
  3. Apply from control01: scripts/lab.sh resume (everything, about 25 minutes), or on control01 a single playbook, for example cd ~/ahmed-infra && git pull && cd ansible && ansible-playbook playbooks/idm.yml.
  4. Add or adjust checks in scripts/test-lab.sh for the new behaviour, including what must be refused.
  5. scripts/lab.sh verify until everything passes. Close the ticket.

9.3 Add a user

  1. Get the person's SSH public key; never their private key.
  2. In ansible/inventory/group_vars/role_idm/identity.yml, add an entry to ipa_users with the next free ID noted in the file, then update the note: 
      - name: nour
    uid: 455400015            # next free ID; the private group gets the same number
    first: Nour
    last: Developer
    groups: [dev]             # the team decides logins (HBAC), sudo and web policy
    sshpubkey:
      - ssh-ed25519 AAAA... nour@laptop
    # home_quota: { soft: 2g, hard: 3g }      # optional, otherwise the default
    # principalexpiration: "2027-03-31Z"     # for temporary staff
  3. If the user needs the VPN, add a peer in role_gateway/main.yml (their WireGuard public key, team, next free address in the team's range).
  4. Commit, push, apply (resume, or idm.yml then site.yml for the home directory and proxy rules).
  5. What happens automatically:
    • The IPA account is created with the fixed UID.
    • Group membership, and through it HBAC, sudo and web policy.
    • The home is created on util01 with its quota.
    • The automount entry covers it (key *).
    • If the team is an allow-list team, the per-user nftables rule includes the new UID.
  6. Test: on control01, ssh -i <key> nour@10.0.2.10, then id, pwd (should be /users/nour on NFS) and sudo -l. Add checks to test-lab.sh (login allowed and denied, sudo, web).

9.5 Remove a user (offboarding)

Know this before your first offboarding ticket
The identity role only ever uses state: present. Deleting a user from identity.yml removes them at the next rebuild (IPA is rebuilt from the file), but not from a running IPA. For same-day offboarding, the code needs a "disabled or absent users" list handled by the role (ipauser with state: disabled or absent). That is a good first ticket. Until then, the emergency step is ipa user-disable <name> on idm01, followed by the code change.

Also: remove the person's VPN peer from role_gateway/main.yml, and decide what happens to their home on util01 (archive it in the backup, then remove it).

9.6 Add a team

Follow the checklist in docs/architecture/org-structure.md:

  1. In identity.yml: the group (next free GID), its users, a host group, an HBAC rule and a sudo rule (or none).
  2. In Terraform: a workstation in hosts (a free IP inside the subnet's 10.0.x.8/29), a VPN range, and the team's workstation security group in team_workstation_sg. Plan, review, apply.
  3. In role_gateway/main.yml: the team's vpn_team_policy and peers.
  4. In all.yml: the team's web policy if it is allow-list, and a team share in storage.yml.
  5. Run site.yml, add tests, verify, record the decision.

SymptomFirst checks
VPN does not connectvpn-client.sh status; sudo wg show ahmed (no "latest handshake" means nothing came back); timeout 5 bash -c '</dev/tcp/<gw01>/443'; did you refresh after the rebuild? Fall back to ssh control01.
A user cannot log inIs their key in identity.yml? id user on the host (SSSD); sssctl domain-status ahmed.internal -o; is there an HBAC rule for the host? journalctl -u sshd or /var/log/secure centrally on util01.
sudo rules missingsudo -l -U user on the host; the identity checksum should have reset SSSD's cache; restart SSSD if it is offline.
Home directory missingsystemctl status autofs; automount -m (maps from IPA); exportfs -s on util01; NFS security group and firewall.

Ansible run hangsLook at ~/run-site.log and ~/ansible.log on control01. Never interrupt dnf. A task over 30 minutes fails on its own.
