13. Interview preparation

Questions you are likely to be asked about this project, with answers you can give in your own words. Every answer is backed by something in the repository you can show.

13.1 The 60-second pitch

"Tell me about this project."
I built the IT environment of a small fictional company on AWS, as its Linux administrator. Terraform builds six RHEL 10 servers in private subnets with default-deny security groups, and Ansible configures everything on them. FreeIPA is the central identity: users, groups, who may log in where, sudo rules, DNS and certificates. Staff connect through a WireGuard VPN with a policy per team, workstations reach the internet only through a Squid proxy with per-user policy, and home directories and team shares come from an NFS server with quotas. Every host sends its logs and audit records to a central log server over TLS. Every host is hardened to the CIS Level 1 benchmark, and an OpenSCAP scan proves it at 100%, with each exception documented. Patching runs in rings with health gates, backups go to S3 and are restore-tested every session, and I run incident drills. The whole lab is destroyed after every session and rebuilt from Git, and 160 automated tests, logging in as real users, prove what is allowed and what is refused. Every decision is documented with its alternatives, and every real incident has a report.

13.2 Design questions

Why FreeIPA and not just local users, or Active Directory?

Local users do not scale and have no central policy. OpenLDAP would mean assembling Kerberos, DNS, sudo and access rules by hand. Active Directory is the enterprise default, but Windows-based. FreeIPA is Red Hat's own product, the Linux equivalent of AD: LDAP, Kerberos, DNS, a CA, HBAC and sudo rules in one, and RHEL's SSSD is its native client (D-006).

Why destroy the lab every session?

It enforces infrastructure as code: anything done by hand is lost, so the code must be complete. It also proves disaster recovery every time (the whole company is rebuilt from Git in about an hour) and removes idle costs, mainly the NAT gateway (D-032, D-048).

How is the network secured?

Default deny at every layer. Only TCP 443 on the VPN gateway faces the internet. Security groups are generated from a list of approved flows, with both halves of every connection declared, so anything unlisted is blocked. Host firewalls repeat the boundary, the VPN gateway has a firewalld policy per team, and SSH is key-only. Each boundary has two independent layers, so one mistake does not open a path (chapter 3.3).

Why does the VPN run inside TLS on port 443?

WireGuard's UDP traffic was being dropped on my network. I proved it with a controlled test: plain UDP on the same port and path got through, WireGuard did not (INC-001). Changing the port would not help, because the traffic is recognised by its content. wstunnel carries the WireGuard packets inside a TLS WebSocket on 443, which looks like HTTPS. WireGuard inside still does all the encryption and authentication.

Why are VPN users not NATed?

So servers see each person's real VPN address. That lets the firewalls tell teams apart, and makes the logs show who did what. It requires disabling the gateway's source/destination check and a return route for the VPN range (D-024).

How do you control which websites people can reach?

Workstations have no route to the internet in their security groups, only to the proxy, so even root cannot bypass it. Squid has one port per policy, and an nftables rule on each workstation, matched on the socket owner's UID, makes allow-list users use their own port. HTTPS is filtered by domain only; there is no TLS interception (D-057).

Why do workstations have no data disks?

All user and team data lives on util01 and is mounted over NFS at login, like company desktops with network homes. A workstation can be lost or rebuilt without losing anything, users see the same files on any workstation, and there is one copy to back up (D-061).

How are secrets handled?

Secrets are encrypted in Git with Ansible Vault. The Vault password is generated by Terraform as an ephemeral value and written to SSM through a write-only argument, so it never appears in state, plan output or any file. Only control01's IAM role can read it, and only through SSM. Hosts enroll in IPA with one-time passwords and never see the admin password (D-043, D-049).

What would you change for production?

  • A second IPA server (replica) to remove the identity single point of failure.
  • Alerting on the log space guard, AIDE and failed drills.
  • Golden images to cut rebuild time.
  • Short-lived SSH certificates instead of a static automation key.
  • Kerberized NFS (krb5p) once users have passwords.
  • Multiple Availability Zones, Ansible execution environments, CI with linters, and IAM Identity Center instead of an access key.

13.3 Troubleshooting stories (the best interview material)

"Tell me about a difficult problem you solved."

INC-007: while hardening SSH for the CIS benchmark, I checked the effective configuration with sshd -T instead of trusting the files, and found every server still offering password logins. sshd keeps the first value it reads, and FreeIPA's drop-in sorted before mine and re-enabled keyboard-interactive. My test had passed because it only tried one authentication method. I renamed my drop-in so it is read first, made every file agree, and wrote a test that checks the methods the server actually offers. Then I wrote an incident report, including the impact: IPA's admin account could have logged in with its password.

DRILL-002: I filled the central log disk on purpose and found messages were lost. My first drill was invalid (I had left 2 MB free and the messages fitted), and my first fix (retrying queues) did not work. The server's own log showed why: rsyslog treats a full disk as a permanent error for a message. So the real defence is to keep the disk from filling, and I added a space guard. I kept all three runs in the report, the failed fix included.

INC-006: a rebuild failed because AWS gave my control node's fixed IP to an AWS-managed endpoint. Earlier builds had passed by luck. I fixed it with subnet CIDR reservations and a Terraform validation that every fixed IP sits inside the reserved block.

How does a user's SSH key reach the server?It is stored in IPA; sshd's AuthorizedKeysCommand asks SSSD (sss_ssh_authorizedkeys), which fetches or caches it
What is HBAC?IPA's host-based access control: rules saying which users may log into which hosts, checked by SSSD during PAM's account phase
Why fixed UIDs?NFS and backups store numbers; a rebuilt IPA must give everyone the same ones
What does idempotent mean?Running it again changes nothing if the system is already right; here, a second site.yml run reports changed=0
Why separate Terraform states?So destroying the lab cannot touch what must survive (Vault password, backups, the state bucket)
What is a tailoring file?An OpenSCAP adjustment of a benchmark profile; here, the deliberate exceptions, each with a reason
RPO and RTO?How much data you could lose; how long recovery takes. Measured here at 649 s and 1 to 2 s against 24 h and 5 to 15 min
What is IMDSv2 and why require it?The token-protected metadata service; it blocks SSRF-style theft of instance credentials
Why is SELinux enforcing?A mandatory layer even root cannot override; data areas get the right labels instead of disabling it

13.5 Known weaknesses (say them before you are asked)

  • One IPA server: identity changes and uncached logins stop while it is down (DRILL-001); a replica is the fix.
  • NFS uses sec=sys: root on a workstation could impersonate other users' IDs (ops have sudo on ws-ops01); krb5p is the upgrade.
  • The per-user web layer can be removed by root on a workstation; the security group still forces everything through the proxy.
  • An instantly full log disk still loses messages; the guard handles the realistic slow case.
  • Single Availability Zone; no alerting system yet.
