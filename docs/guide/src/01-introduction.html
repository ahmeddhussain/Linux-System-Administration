1. The project in one chapter

1.1 What this project is

ahmed-infra is a complete, working IT environment for a fictional company called ahmed, built on Amazon Web Services (AWS). You play the company's Linux system administrator. The lab contains what a real Linux administrator owns in a company: central user accounts and passwords policy, who may log in where, who may use sudo, a VPN for remote staff, firewalls, an internet proxy that decides which websites each team may reach, file servers for home directories and team shares, central logging, security auditing, compliance scanning against an industry benchmark, a patching process, backups with tested restores, and rehearsed incident drills.

Everything is code. The servers, networks and firewalls are described in Terraform; everything that happens inside the servers is described in Ansible. Nothing is configured by hand. To prove that, the whole lab is destroyed after every working session and rebuilt from Git at the start of the next one. If something was done by hand and not written into code, it disappears, so it is impossible to cheat.

Why the workstations have no data disks
Workstations hold no user or team data at all (D-061). Users' home directories and the team shares live on util01's data disks and are mounted over the network (NFS) when a user logs in. A lost or rebuilt workstation therefore loses nothing; the same files appear on any workstation; there is exactly one copy of every file, and it is backed up with util01. This is how company desktops work with network home directories. The workstation disk is 10 GiB because that is the minimum the RHEL image allows.

1.4 The principles everything follows

  1. Terraform builds, Ansible configures (D-003). Terraform creates what AWS provides (network, servers, disks, firewall rules in AWS, IAM permissions). Ansible configures the operating system and the services on top.
  2. Everything is code and the lab is rebuilt every session (D-032, D-048). Manual repairs are allowed only to rescue a broken host, and must be followed by a code change that prevents the problem from coming back.
  3. Default deny (D-019). No network connection is possible unless it is written down in terraform/network-policy.tf. Firewalls on the hosts repeat the same boundary as a second layer.
  4. Data, not code, for day-to-day changes. Adding a user, a team, a VPN peer or a website to a block list means editing a data file under ansible/inventory/group_vars/, never the logic.
  5. Secrets never in Git, logs or Terraform state (D-042, D-043). Secrets are encrypted with Ansible Vault; the Vault password lives in AWS SSM and only control01 can read it.
  6. Every decision is recorded with its alternatives and why it was chosen (Decisions.md, D-001 to D-069). Every real failure gets an incident report (INC-001 to INC-007).
  7. Prove it with tests. scripts/test-lab.sh runs 160 checks, logging in as real users and proving both what is allowed and what is refused.

Chapters 4 and 5 walk through the Terraform and Ansible code file by file and role by role. Chapter 6 explains the scripts.
