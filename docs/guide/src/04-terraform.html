4. Terraform, file by file

Terraform creates everything AWS provides. This chapter explains every file, so you can read any line of the code and know why it is there.

4.1 The lab layer: terraform/

Every host is one entry. The fields:

Validations on the map: every subnet exists; every role or security group is a known role; every IP is a valid IPv4 address; no two hosts share an IP; every IP lies inside its subnet's reserved block (D-062); root volumes are at least 10 GiB; exactly one control node. Adding a server is therefore one entry, and Terraform catches mistakes before AWS sees them.

4.3 The modules

modules/network

  • The VPC (DNS support and hostnames on), an internet gateway, one subnet per entry of var.subnets (public subnets give instances public IPs; private ones never do).
  • Subnet CIDR reservations (aws_ec2_subnet_cidr_reservation, type explicit) for 10.0.x.8/29 in every subnet. AWS never hands those addresses to managed interfaces such as the NAT gateway or the Instance Connect Endpoint (INC-006, D-062). The module's subnet_ids output and the NAT gateway depends_on the reservations, so nothing is placed in a subnet before its addresses are protected.
  • A NAT gateway with its Elastic IP in the public subnet, switchable with enable_nat_gateway.
  • Route tables: public (default route to the internet gateway) and private (default route to the NAT).
  • Mocked tests (tests/nat.tftest.hcl): NAT on by default, NAT off removes all NAT cost, only public subnets map public IPs, every subnet has an explicit reservation.

modules/security-groups

  • One empty security group per role. "Empty" means everything is denied.
  • The VPC's built-in default security group is taken over and stripped of all rules, so nothing can accidentally use it.
  • For every flow (role A to role B on a port) it creates both halves: an egress rule on A that references B's group, and an ingress rule on B that references A's group. With default-deny egress, a connection needs both.
  • cidr_ingress and cidr_egress maps create rules for IP ranges (the VPN ranges, the VPC, the internet).
  • Rules are separate resources (aws_vpc_security_group_*_rule), never inline, which avoids circular references between groups (D-015).
  • Mocked tests: one group per role, each flow opens exactly its two halves and nothing else, and flows or rules naming an unknown role are rejected.

modules/ec2-instance

  • The instance, with its fixed private IP, security group, bootstrap key and optional IAM instance profile.
  • cloud-init user data sets the hostname and FQDN (<name>.ahmed.internal), which FreeIPA requires.
  • IMDSv2 required, hop limit 1: containers or proxies on the host cannot reach the metadata service.
  • An encrypted gp3 root disk; extra encrypted gp3 volumes and their attachments from extra_volumes.
  • An optional Elastic IP.
  • lifecycle { ignore_changes = [ami, user_data] }: when Red Hat publishes a newer image, Terraform does not replace the servers. They are patched in place with dnf instead (D-021, D-034).

4.4 network-policy.tf: the firewall policy as data

The file defines four things, and the security-groups module turns them into rules:

  1. Roles: eice, gateway, control, idm, util, workstation-dev, workstation-ops. Each team's workstation has its own group, so AWS enforces the same per-team boundary as gw01's firewall (D-052).
  2. Flows (role to role):
    • Instance Connect to control01 on SSH; control01 to every other role on SSH (Ansible).
    • Workstations to util01 on 3128 and 3129 (Squid), on 2049 (NFSv4).
    • Every role except util to util01 on 6514 (logs over TLS).
  3. Ingress from IP ranges:
    • The internet to gw01 on TCP 443, only if enable_vpn_endpoint.
    • The admin VPN range to control01 and both workstations on SSH and ICMP.
    • Each team's VPN range to its own workstation on SSH; the ops range to idm01 and util01 on SSH (D-053).
    • The whole VPC to idm01 on the FreeIPA ports (DNS 53 TCP/UDP, Kerberos 88 and 464 TCP/UDP, LDAP 389, LDAPS 636, HTTP 80 for certificate revocation, HTTPS 443); the admin range to idm01 on 443 (web UI); ICMP inside the VPC.
  4. Egress to IP ranges:
    • Servers (not workstations) may use HTTPS to the internet through the NAT, for packages.
    • Every role may send ICMP inside the VPC.
    • Every role may reach idm01's single address on the FreeIPA ports (HTTPS only for workstations, since servers already have it).
    • gw01 may forward VPN SSH into the infra and workstation subnets: security group egress also applies to forwarded packets (D-024).
Why FreeIPA uses the VPC range instead of role-to-role flows
Every host in the VPC is an IPA client by design, so "from the VPC" is the honest boundary, and each host's egress is still pinned to idm01's single /32. Role-to-role flows for ten ports and six roles would be about 72 rules, near AWS's default limit of 60 rules per group (D-051).
Opening a new connection (the change procedure)
Add one entry to flows (or the CIDR maps), run terraform plan, check that it adds exactly the two rules you expect, apply, and record it. Anything not written here stays denied.

4.6 The persistent and bootstrap layers

terraform/persistent

  • The Ansible Vault password: an ephemeral "random_password" (64 characters) written to the SSM SecureString /ahmed-infra/ansible-vault-password through the write-only argument value_wo. The password never appears in plan output, in state or on disk (D-043). Rotation means re-keying every vault file and bumping vault_password_version.
  • The backup bucket ahmed-infra-backups-<account>: versioning (old versions expire after 30 days), public access blocked, SSE-S3 encryption, owner-enforced objects (no ACLs), and a policy that denies any request not made over TLS. prevent_destroy on everything.

terraform/bootstrap

The state bucket ahmed-statefile existed before the code did, so it is adopted with import blocks rather than recreated (D-044): versioning (old state versions expire after 90 days, so an overwritten state can be recovered), public access blocked, encryption, a TLS-only policy, prevent_destroy. Its own state lives in the same bucket. If the bucket were ever lost, the backend block is commented out and the layer applied locally.

4.7 Terraform tests

terraform test runs plans against a mocked AWS provider, so no credentials are needed, nothing is created, and they take seconds (D-045). The root tests check that the default six-host inventory plans, and that each validation rejects what it should: an unknown subnet, an unknown role, a duplicate IP, two control nodes, an IP outside the reserved block. The module tests are listed in 4.3. Run them with:

terraform -chdir=terraform test
terraform -chdir=terraform/modules/network init -backend=false && terraform -chdir=terraform/modules/network test
terraform -chdir=terraform/modules/security-groups init -backend=false && terraform -chdir=terraform/modules/security-groups test

4.8 What happens on terraform apply (lab layer)

  1. VPC, internet gateway, subnets, route tables, the default security group stripped.
  2. Subnet CIDR reservations; only then the NAT gateway (and its EIP), the subnet outputs and anything placed in a subnet.
  3. Security groups and their rules (about 120 rule resources).
  4. Key pair, IAM roles and instance profiles.
  5. The six instances (with fixed IPs inside the reservations), util01's data volumes and attachments, gw01's EIP.
  6. The Instance Connect Endpoint and the VPN return route.

The whole layer is 169 resources. terraform plan -destroy before every teardown confirms that only those are touched: never the SSM parameter, the backup bucket or the state bucket.
