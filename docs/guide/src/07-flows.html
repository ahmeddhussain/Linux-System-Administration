7. How it works end to end

The best way to understand the design is to follow real requests through every layer. These are also the stories to tell in an interview.

7.1 sara logs into ws-ops01 from home

  1. VPN. On her laptop, wstunnel opens a TLS connection to gw01's public IP on TCP 443. WireGuard's UDP packets travel inside it. gw01's wstunnel hands them to WireGuard on localhost UDP 51820. WireGuard accepts them only because they are signed by sara's peer key, and they arrive on wg0 from her fixed VPN address in the ops range (10.8.2.x).
  2. gw01's firewall. Her source address falls in the firewalld zone vpn-ops. The forwarding policy for ops allows ws-ops01:22, idm01:22 and util01:22, and nothing else, so the packet is forwarded out of gw01's interface. AWS lets gw01 forward it because its source/destination check is disabled, and gw01's security group egress allows forwarded SSH into the workstation subnet.
  3. AWS security group. ws-ops01's group workstation-ops accepts SSH from 10.8.2.0/24 (and from admin), and from no other team's range.
  4. Replies go back through the private route table's 10.8.0.0/16 → gw01 route, because there is no NAT: ws-ops01 sees sara's real VPN address.
  5. sshd. Only public-key authentication is offered. sshd asks SSSD for sara's public key (sss_ssh_authorizedkeys, set up by the IPA client). SSSD fetches it from IPA's LDAP, or serves it from its cache.
  6. HBAC. In the PAM account phase, SSSD checks IPA's HBAC rules: ops may log into the ops workstations and the servers host group. A dev user would be refused here even with a valid key.
  7. Home directory. sara's home is /users/sara. autofs on ws-ops01 has IPA's map (auto.home, key *), so it mounts util01.ahmed.internal:/export/home/sara over NFSv4 on TCP 2049. util01 exports only to the workstation addresses; the files belong to UID 455400010, the same number everywhere because IDs are fixed (D-060).
  8. Shell. /etc/profile.d/ahmed-proxy.sh sets her proxy to the standard port; the 15-minute idle timeout and umask 027 apply.
  9. sudo. sudo -i works because IPA's ops-all rule covers ws-ops01, delivered by SSSD, with no password (logins are key-only). sudo writes to /var/log/sudo.log, and auditd records the sudo command (USER_CMD) and every command she then runs as root (key privileged). Both travel to util01, where laila can search them.

7.2 ahmed (dev) opens a website

  1. His shell's https_proxy points at util01.ahmed.internal:3128 (standard policy, team dev).
  2. The workstation's security group allows only util01:3128/3129, so there is no other way out: a direct connection to the internet simply times out.
  3. Squid receives CONNECT www.youtube.com:443, matches the streaming deny list on the standard port, and answers 403. CONNECT example.com:443 is allowed; Squid opens the connection through util01's NAT egress, and the TLS session runs end to end between the browser and the site. Squid sees only the domain.
  4. If contractor1 (allow-list team) on the same machine pointed his browser at port 3128 to escape his policy, the nftables rule on ws-dev01 rejects any packet to util01:3128 owned by his UID, so he only works on 3129, where only the allow-list passes.
  5. Squid's access log is also sent to syslog, so it ends up centrally on util01.

7.3 A log line travels to util01

  1. A program on ws-dev01 logs to the journal. rsyslog reads it (imjournal).
  2. rsyslog forwards it over TCP 6514 with TLS, presenting ws-dev01's certificate from the IPA CA (requested and renewed by certmonger) and checking that the server is util01.ahmed.internal.
  3. util01 accepts only senders with a valid IPA certificate, looks up the sender's address in reverse DNS, and writes /srv/logs/ws-dev01.ahmed.internal/<program>.log, group security, mode 0640.
  4. If util01 is down, the sender keeps the messages in its disk queue and retries every 10 seconds.
  5. Audit records follow the same path (auditd's syslog plugin), but are written raw to audit.log so the audit tools can read them.

7.4 A new host joins the company (enrollment)

  1. Terraform creates it with a fixed IP inside the reserved block, a FQDN set by cloud-init, and tags Role/Team. The dynamic inventory immediately puts it in the right Ansible groups.
  2. bootstrap.yml creates the ansible account; patch.yml brings it to the fleet's patch level; base applies the baseline.
  3. In idm.yml, ipa_client_prepare creates a one-time password for it on idm01 and registers it in DNS. ipaclient enrolls it: it points its resolver at idm01, gets a host keytab, configures SSSD, publishes SSHFP records, and points sshd at SSSD for keys.
  4. Host groups, HBAC and sudo rules apply to it as soon as it is in the right host group; ipa_client_config resets SSSD's cache when the identity data changed.
  5. The log, audit, client, and hardening roles follow. Its compliance scan and the tests prove it.
