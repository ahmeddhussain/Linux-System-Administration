6. The scripts

6.1 scripts/lab.sh: the lab's front door

Everything starts on the laptop with lab.sh. It is a thin entry point over three libraries in scripts/lib/ (D-032, D-041):

CommandWhat it does
up [-y]Terraform apply (lab layer), then everything resume does. About an hour from nothing. -y approves the plan automatically.
resumeOn existing infrastructure: load the bootstrap key into the SSH agent; write the SSH config; wait for control01; prepare control01; bootstrap the ansible account; run site.yml detached and poll it; reboot control01 if patching needs it; run the compliance scan and the restore drill; run the tests; refresh the VPN client
verify [--full]The tests only; --full adds a full site.yml run that must change nothing
compliancePull on control01, run the CIS scan, publish the results
patch [--security]The patch cycle in rings, then the tests
drill <name>restore, idm-outage, logs-disk-full or package-rollback
statusShow the instances
down [-y]Disconnect the VPN, back up util01 to S3 (it asks before destroying if the backup fails), then terraform destroy of the lab layer only

The libraries

  • lib/common.sh: paths, region, the key (~/.ssh/ivolve.pem, overridable with LAB_SSH_KEY), log/warn/die, a tool check, and a lookup of a host's instance ID by its Name tag.
  • lib/infra.sh: infra_apply (init and apply), infra_destroy (backup first, then destroy), infra_status.
  • lib/control01.sh: writes ~/.ssh/ahmed-lab.conf with two entries, then waits, prepares and reboots control01 as needed.
    • control01 goes through Instance Connect (aws ec2-instance-connect open-tunnel) and always works: it is the break-glass path.
    • control01-vpn goes to 10.0.1.10 over the VPN, with the host key stored under the instance ID.
  • lib/configure.sh: run_on_control01, plus configure_hosts, run_compliance, run_patch_cycle, run_drill and run_tests.
    • run_on_control01 is the key helper. It starts a long command detached on control01 (setsid nohup, output to ~/run-<name>.log, exit code to ~/run-<name>.rc), then follows it with short SSH calls every 20 seconds, printing new PLAY and TASK lines. A long SSH session through the Instance Connect tunnel had stalled before (INC-002), so long jobs never depend on one connection staying up.
Why the login banner repeats during up
Every poll is a new SSH connection, and sshd prints the company banner to each one. It is cosmetic: the job is running on control01 regardless.

6.2 scripts/control01-setup.sh

Piped to control01 over SSH, safe to rerun:

  1. Installs git and Python, with retries, because the repositories can take a minute after first boot.
  2. Clones the repository, or pulls it with --ff-only.
  3. Creates the venv and installs the pinned requirements.txt and collections.
  4. Generates the ansible_ed25519 key if missing, and activates the venv in .bashrc.

Everything is inside a function that runs with stdin closed, so no command can swallow the rest of the piped script.

6.3 scripts/vpn-client.sh (laptop)

CommandEffect
refreshFetches the gateway's public key and the current public IP, and writes /etc/wireguard/ahmed.conf. Run after every rebuild, because the Elastic IP is new each time.
connectStarts wstunnel as a user systemd unit (ahmed-wstunnel) towards wss://<gw01>:443, brings up WireGuard (MTU 1280, route for 10.0.0.0/16 only: a split tunnel), and pings control01
disconnect, statusStops both, or shows the state

It needs sudo for /etc/wireguard. During a long up the sudo prompt times out, so run refresh by hand afterwards.

6.4 scripts/test-lab.sh: 160 checks

Copied to control01 and run there by lab.sh verify. Helpers:

  • check: a command must succeed.
  • reach: a TCP port from one host to another must be open or blocked.
  • as_user/as_check: log in as a real IPA user with their key and run something.
  • login and sudo_as: a login or a sudo must be allowed or denied.
  • web: the proxy's answer for a user and URL: 200 allowed, 403 denied by policy, 000 refused by nftables.
  • VPN test peers, one per team, in network namespaces on control01, carried through wstunnel to gw01 like a real client (D-055).

The users' private test keys are decrypted from the vault into /dev/shm (memory only) and removed on exit. Sections:

  • Inventory and access
  • Network policy (default deny, including "must be blocked")
  • Baseline configuration (SELinux, firewall, SSH, banners; key-only proven)
  • Patch level and patch records
  • VPN gateway
  • util01 data volume and backups
  • Time and identity (FreeIPA, SSSD, IDs, SSHFP, no allow_all, pinned names)
  • Logins and sudo per team
  • Central logs over TLS, log space guard
  • Audit records
  • Hardening: crypto policy, AIDE
  • OpenSCAP compliance
  • Restore drill
  • NFS homes
  • Storage, quotas, team shares
  • Web access per user
  • Per-team VPN policy
  • Idempotency (with --full)

A test tests denial as much as access: "contractor1 login on util01 is denied", "ahmed cannot delete sara's file in the company share", "WireGuard UDP port is closed to the outside". Default-deny designs usually fail exactly there (D-035).

6.5 Small helpers

  • ansible/scripts/vault-password.py: Ansible's vault_password_file. It reads the SSM parameter with control01's instance role (boto3) and prints it; on error it says what failed, never the value.
  • Scripts on util01, installed by roles:
    • ahmed-backup: backup, restore, verify and drill (6.6).
    • ahmed-audit-report: today's audit summary per host.
    • ahmed-logspace: the space guard.

6.6 ahmed-backup (util01)

ModeWhat it does
backuptar of homes, team shares and logs (with ACLs, extended attributes and SELinux labels; NFS silly-rename files .nfs* excluded), streamed by aws s3 cp - into s3://ahmed-infra-backups-<account>/util01/latest.tar.gz. A tar exit code of 1 ("a file changed while being read", which growing logs cause) is a warning; 2 is a failure.
restoreStreams the latest backup back and extracts it onto /. Used on a new volume.
verifyDownloads and lists the whole archive
drillThe restore drill:
  1. Measures the RPO (time since the data was last safe).
  2. Plants a marker file in ahmed's home and takes a real, timed backup.
  3. Deletes the marker and restores just that file. Content, owner by name and SELinux label are checked.
  4. Restores everything into /var/tmp/restore-drill and compares homes and team shares with live (full RTO).
  5. Writes PASS or FAIL against targets of RPO 24 h, single file 5 min, all data 15 min.

Owners are stored and restored by name. After an IPA reinstall the numbers could differ, and names map files back to the right people (D-056 as built, D-060).
